**`hyperag2api`** — производительный кросс-платформенный **OpenAI-совместимый** прокси-сервер для **[Hyperagent.com](https://hyperagent.com)**. Он поднимает локальный эндпоинт `/v1/chat/completions` и проксирует запросы в бэкенд Hyperagent, используя сессию твоего залогиненного браузера — так продвинутые модели (*Claude Opus 4.8*, *GPT 5.6*, *Gemini 3.5*, *Grok 4.5* и др.) доступны из **OpenCode**, **Continue**, **Cursor** или любого своего OpenAI-клиента.

---

## ✨ Возможности

- 🧵 **Сессия → тред** — один тред Hyperagent на разговор, переиспользуется между ходами. Вместо создания нового треда (и повторной отправки всей истории) на каждый запрос прокси распознаёт продолжение диалога и шлёт только новое сообщение. Опциональная **персистентность на SQLite** сохраняет привязку между перезапусками, а **именованные сессии** позволяют закрепить тред явно.
- 🧠 **Показ размышлений** — reasoning модели стримится как OpenAI `reasoning_content` и/или встроенными тегами `<think>…</think>` (`REASONING_STYLE`).
- 🛡️ **Стабильность** — кэш cookie с коротким TTL поверх одного CDP-подключения, авто-переавторизация при 401/403, раздельные таймауты connect/stream, ретраи с экспоненциальной задержкой, устойчивый разбор SSE и keepalive-heartbeat, чтобы длинные генерации не отваливались по таймауту.
- 🔧 **Проброс tool-calls** — активность инструментов бэкенда можно отдавать как OpenAI `tool_calls`-дельты (`TOOLCALL_MODE`).
- 🔌 **Клиентский tool-calling (MCP / функции)** — мост OpenAI function-calling поверх текстового агента Hyperagent: клиенты вроде **OpenCode** могут использовать **свои** MCP-серверы/функции через прокси. Прокси принимает `tools`, заставляет модель выдать `tool_calls` с `finish_reason: "tool_calls"` и возвращает твои результаты `role:"tool"` обратно в тот же тред. Проверено вживую.
- 🖼️ **Мультимодальный ввод** — части контента `image_url` загружаются через `/api/files/upload` и привязываются к треду через `/api/threads/{id}/attachments`.
- 📊 **Живая панель** — read-only монитор на `/dashboard` (плюс JSON на `/api/stats`): активные сессии, последние запросы, задержки, токены, состояние браузера/cookie.
- ❤️ **Health-проба** — `/health` показывает связь с браузером и состояние логина.

> Режим планирования по умолчанию **выключен** (`INJECT_PLAN_MODE=0`): модель выполняет работу, а не только предлагает план. Steering/`AskQuestion` при этом по-прежнему распознаётся и отображается.

## ⚡ Требования

Чтобы корректно снимать сессионные cookie, нужен **хотя бы один браузер на Chromium**, которым лаунчер сможет управлять по CDP. Автоопределяются:

- 💻 **Microsoft Edge** (рекомендуется)
- 🌐 **Google Chrome**
- 🦁 **Brave Browser**
- 📦 **Chromium**
- 🎭 **Playwright-Chromium** (ставится через `playwright install chromium` — определяется автоматически, системный браузер не нужен)

Определение работает на **Windows, macOS и Linux**.

> [!NOTE]
> Firefox отображается, если установлен, но его режим удалённой отладки CDP экспериментальный. Для надёжной синхронизации cookie рекомендуются браузеры на Chromium.

## 📦 Установка

### Вариант A — Автоматический установщик (рекомендуется)

Ставит зависимости Python **и** Playwright-Chromium, проверяет окружение и печатает найденные браузеры:

```bash
python3 install.py
```

Полезные флаги:
- `python3 install.py --skip-browser` — только зависимости (будешь использовать системный браузер).
- `python3 install.py --with-deps` — также поставить системные библиотеки браузера (Linux; может потребоваться `sudo`).

### Вариант B — Вручную

```bash
pip install -r requirements.txt
playwright install chromium   # необязательно, если уже есть Edge/Chrome/Brave
```

> Требуется **Python 3.9+**.

## 💻 Запуск лаунчера

Запусти интерактивную консоль на **Linux, macOS или Windows**:

```bash
python3 start.py
```

### 🔍 Пайплайн запуска
1. **Определение платформы** — Windows, macOS или Linux автоматически.
2. **Сброс квоты/сессии** — предложит очистить cookie, если кончилась квота или нужен другой аккаунт.
3. **Настройка API-ключа** — опционально включить защитный API-ключ (пусто = принимать любой).
4. **Автопоиск браузера** — сканирует систему **и** Playwright и даёт выбрать браузер.
5. **Обратный отсчёт** — запускает браузер в режиме отладки с выделенным профилем и отсчитывает время, пока ты логинишься на `https://hyperagent.com`.
6. **Сплит-панель** — локальные/глобальные IP, порты и инструкции. Нажми любую клавишу, чтобы показать живые логи трафика.
7. **Хоткей сброса** — нажми `Ctrl + N` при активных логах, чтобы мгновенно сбросить cookie, перезапуститься и войти заново.

> [!TIP]
> Отладочный браузер использует выделенный постоянный профиль в твоей пользовательской папке. Это сохраняет логин между перезапусками **и** гарантирует, что порт отладки откроется, даже если обычный браузер уже запущен.

## 🔌 Клиентский tool-calling (MCP / функции)

Прокси реализует цикл OpenAI tool-calling **поверх** серверного агента Hyperagent, чтобы клиенты вроде **OpenCode** могли использовать **свои** MCP-серверы / функции через него:

1. Клиент шлёт `tools` (описания функций) вместе с запросом.
2. Прокси вшивает в разговор «контракт использования инструментов»; модель пишет запрос `<tool_call>{…}</tool_call>`, который прокси превращает в OpenAI `tool_calls` с `finish_reason: "tool_calls"`.
3. Клиент выполняет тул (свой MCP-сервер) и присылает результат `role:"tool"` обратно.
4. Прокси отправляет результат в **тот же** тред Hyperagent, и модель продолжает — новые вызовы или финальный ответ.

Режим включается автоматически, как только в запросе есть `tools` (настройка не нужна). `tool_choice` поддерживает `auto` (по умолчанию), `required`, `none` и конкретную `{function}`.

**Экономия токенов:**
- Полный блок схем инструментов вшивается **один раз на тред**; на последующих ходах того же разговора — только однострочное напоминание. Если набор инструментов **изменился** (например, добавил новый MCP-сервер), прокси видит новую сигнатуру и автоматически пере-высылает полные схемы.
- JSON-схемы инструментов **минифицируются**, и всегда отправляется только дельта нового хода (за счёт переиспользования треда), а не вся история.

**Гибридный стриминг:** обычные ответы стримятся **токенами** даже при наличии `tools`; прокси начинает буферизовать только когда появляется сентинел `<tool_call>` (частичный сентинел на границе токенов придерживается и никогда не утекает в вывод).

> **Добавляешь новые клиентские MCP?** На стороне прокси делать ничего не нужно. OpenCode сам добавляет функции всех MCP в `tools` каждого запроса, а прокси tool-agnostic — новые инструменты просто появляются и становятся вызываемыми. Добавь их посреди разговора — прокси пере-праймит тред обновлёнными схемами.

**Серверные тулзы/MCP не мешают:**
- Во время tool-хода прокси принудительно **выключает** собственные возможности Hyperagent (веб-поиск, браузер, код, интеграции, режим планирования), чтобы **серверный агент делегировал всё клиенту**, а не делал своё. Управляется `DISABLE_SERVER_MCP` (по умолчанию вкл). `enabledIntegrations` всегда пустой — собственный MCP Hyperagent не срабатывает.

**Заметки и ограничения:**
- Это **мост на уровне промпта**, а не нативный function-calling — надёжен для типичного цикла с одним/параллельными вызовами, но не гарантирован для всех крайних случаев. Основной формат вызова — `<tool_call>{…}</tool_call>`; fenced ```tool_call``` / ```json``` парсятся как запасной вариант.
- Функции выполняются **на стороне клиента** (твой MCP), а не в Hyperagent — поэтому работает **любой** клиентский MCP (Figma, filesystem, GitHub, …); прокси tool-agnostic.
- Много инструментов = больше разовая преамбула; для больших наборов и долгих циклов закрепляй разговор `X-Session-Id` (или `model@session`).

## 🔑 Режим без браузера (сессии из конфига)

Не хочешь запускать браузер? Задай токен сессии напрямую — и прокси полностью пропускает Playwright/CDP. Удобно для серверов и headless-окружений.

Возьми значение cookie **`__Host-hyperagent_session`** из залогиненного браузера (DevTools → Application → Cookies → `hyperagent.com`), затем:

```bash
# один аккаунт
HYPERAGENT_SESSION="<значение cookie>" python3 proxy_server.py

# несколько аккаунтов (ротация при ошибке авторизации)
HYPERAGENT_SESSIONS="tokenA,tokenB" python3 proxy_server.py

# или из файла (по токену на строку, либо JSON-массив)
SESSIONS_FILE=~/.hyperagent-sessions python3 proxy_server.py
```

| Переменная | По умолчанию | Описание |
| :--- | :--- | :--- |
| `SESSION_MODE` | `auto` | `auto` (конфиг если задан, иначе браузер), `config` (никогда не трогать браузер), `browser`. |
| `HYPERAGENT_SESSION` | *(не задан)* | Одно значение `__Host-hyperagent_session`. |
| `HYPERAGENT_SESSIONS` | *(не задан)* | Значения через запятую (несколько аккаунтов). |
| `SESSIONS_FILE` | *(не задан)* | Путь к файлу: токен на строку или JSON-массив. |

Прокси **проверяет каждую сессию при старте** (через `/api/auth/me`) и логирует, чей это аккаунт. Проверить в любой момент:

```bash
curl -s localhost:<PORT>/accounts | jq
# → {"mode":"config","accounts":[{"valid":true,"email":"you@example.com","name":"...","session":"…6fb8"}], ...}
```

Токены никогда не логируются целиком — только отпечаток `…last4`. Относись к значению сессии как к паролю.

> **Баланс/кредиты:** не показываем — Hyperagent не отдаёт их через публичный API-эндпоинт (проверено). `/accounts` подтверждает, что сессия рабочая и чей это аккаунт; за балансом — на страницу биллинга Hyperagent.

> **Playwright теперь опционален** — нужен только для режима `browser`. В режиме конфига прокси работает без него.

## ⚡ Задержки — чего ждать

Время ответа определяется **бэкендом Hyperagent**, а не прокси. Каждый тред работает в облачном сэндбоксе, который поднимается по требованию. Замерено вживую:

| Состояние | Время до первого токена |
| :--- | :--- |
| **Холодное** (новый тред / новый разговор) | ~10 с (сэндбокс поднимается ~3.7 с, потом работает агент) |
| **Горячее** (сэндбокс уже поднят, следующее сообщение) | **~0.1 с** |
| После **~40 с простоя** | снова холодное — сэндбокс выгружается |

Два честных вывода:

- **В активном диалоге — быстро.** Прокси переиспользует один тред на разговор, поэтому пока сообщения идут с интервалом менее ~40 с, сэндбокс остаётся горячим и ответы почти мгновенные. Большие задержки, которые ты видишь, — это **холодные старты**: первое сообщение разговора или сообщение после паузы (иногда 40–80 с под нагрузкой бэкенда).
- **Бесплатного keep-alive нет.** Мы протестировали периодический пинг `warm` — он **не** держит сэндбокс горячим (только реальная активность держит). Поэтому прокси не тащит фейковый keep-alive; настоящий стоил бы прогона модели на каждый пинг и засорял бы тред — оно того не стоит.

Что прокси реально делает для скорости:
- **Переиспользование треда** держит сэндбокс горячим в активной сессии.
- **`LOW_LATENCY_MODE`** (по умолчанию вкл) выключает серверные тулзы + plan mode → самый быстрый и дешёвый ответ.
- **SSE-heartbeat** во время долгих ожиданий держит соединение, чтобы холодный старт 40–80 с не отвалился по таймауту клиента.

"provider": {

## ⚖️ Дисклеймер

`hyperag2api` работает через твою **собственную** авторизованную сессию Hyperagent и его веб-эндпоинты. Это неофициальный community-проект, не связанный с Hyperagent. Используй его в соответствии с условиями использования Hyperagent и только с аккаунтом, которым владеешь. Держи сессионные cookie в секрете — относись к ним как к паролю.
